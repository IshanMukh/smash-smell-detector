SMELL DEFINITIONS AND DETECTION STRATEGIES:
 
1. God Class
Definition: A class that has grown too large and taken on too many responsibilities. It handles things that should belong to separate classes.
How to detect:
- Count the number of PUBLIC METHODS. A God Class typically has 8 or more public methods covering clearly different concerns.
- Count DISTINCT RESPONSIBILITIES. Ask yourself: does this class do data access AND business logic AND serialization AND coordination? Each of those is a separate responsibility. If yes, it is a God Class.
- DO NOT flag a class as God Class just because it has many fields. A data class, DTO, value object, or simple model class with many fields but ONE responsibility is NOT a God Class.
- DO NOT flag a class as God Class if it has fewer than 5 methods, regardless of how many fields it has.
- Evidence required: you must name at least 2 clearly different responsibilities visible in the code.
 
2. Hub-Like Dependency
Definition: A class that is highly connected to many other components, acting as a central hub. Changes to it or its dependencies cause widespread ripple effects.
How to detect:
- Count ALL external classes this class depends on (imports, field types, constructor parameters, method parameters, return types).
- Only report Hub-Like Dependency if the total number of distinct external dependencies is 6 or more.
- The dependencies must be meaningful collaborators, not utility classes like String, List, Map, Logger, or standard Java/language types.
- Evidence required: list the specific external class names. If you cannot name 6 real collaborators, do not report this smell.
 
3. Unstable Dependency
Definition: A class depends on other classes that are likely to change frequently, making it vulnerable to ripple effects.
How to detect:
- Only report this if you can see clear evidence that the class depends on volatile, implementation-heavy collaborators rather than stable abstractions or interfaces.
- Signs: depends directly on concrete implementations rather than interfaces, depends on classes with names suggesting they are actively changing (Repository, Factory, Module, Manager).
- DO NOT report this based on one or two dependencies alone. You need to see multiple volatile dependencies.
- Evidence required: name the specific volatile dependencies and explain why they appear unstable.
 
4. Cyclic Dependency
Definition: This class and one or more other classes depend on each other in a cycle.
How to detect:
- This is very hard to confirm from a single class. Only report if you can see explicit evidence of circular references in the code shown.
- Signs: the class imports or references another class that appears to reference back to this class based on naming or visible code.
- When in doubt, DO NOT report this. False positives here are costly.
- Evidence required: name both directions of the cycle explicitly.
 
5. Cyclic Hierarchy
Definition: A parent class depends on one of its own child classes, creating a circular inheritance relationship.
How to detect:
- Only report if you can see that this class is a supertype AND it explicitly imports, references, or uses one of its known subtypes.
- Signs: an abstract or base class that has a field or method parameter typed as one of its concrete implementations.
- Evidence required: name the specific subtype being referenced from the parent.
 
6. Deep Hierarchy
Definition: The inheritance chain is excessively deep, making behavior hard to trace and understand.
How to detect:
- Count the inheritance levels visible in the extends/implements chain.
- Only report if the chain is 3 or more levels deep AND the class relies heavily on inherited behavior (many overrides, calls to super).
- A class that extends one abstract class is normal. A class that extends a class that extends a class that extends another class is Deep Hierarchy.
- Evidence required: write out the full visible inheritance chain.
 
7. Wide Hierarchy
Definition: A hierarchy has too many direct subclasses of one parent with no useful intermediate abstractions between them.
How to detect:
- This is hard to confirm from a single class. Only report if the class shows clear signs of being one of many siblings in a flat hierarchy with no intermediate abstractions.
- Signs: many sibling class names visible in imports or method signatures, all implementing the same interface directly.
- Evidence required: name the sibling classes visible in the code.
